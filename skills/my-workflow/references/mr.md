# 开了 MR 之后怎么做

你开了 MR，后面的事都归你：等 review、改意见、等流水线、找人合并、合并之后的发布和验证，直到任务真的做完。
看板不替你做这些，只把 MR 上发生的事告诉你。

## 开完 MR：盯着它

- 开完 MR 马上（同一轮里）用 `wait_for` 盯着它：`wake` 里加一项 `message`，`conversation` 填 MR 地址，`what` 写现在在等什么（等 review、等流水线、等谁合）。
  然后结束这一轮。
- 不写 `until`，就是「从现在起有新情况就叫醒」：合并了 / 被关了、别人多了新意见、流水线跑完（过了或挂了）、出现冲突、要变基、可以合了。
  只关心其中几样就写 `until`，它是一个 JS 表达式，字符串要加引号。比如只等合并：`"until": "state != 'opened'"`；
  只等流水线和意见：`"until": "pipeline == 'failed' || reviews > 3"`（`reviews` 写现在的条数，不然处理完再等会马上又被叫醒）；
  只等别人还没解决的意见：`"until": "notes.some(n => n.author != me && n.resolvable && !n.resolved)"`。字段见 `gerdr wait sources`。
- 判断的是 MR 当时的样子，所以晚一点才等也不会错过：已经发生的，一等就叫醒你。
- 叫醒你的消息里有 MR 现在的各个字段、最近的意见、流水线挂了时失败 job 的日志末尾。这次等待随之结束：
  处理完还要等的，就再 `wait_for` 一次，`what` 写成新的状态。

## 有新的 review 意见

- 一条一条看。要改的就改，推到同一个分支，在那条讨论下回一句改了什么（`glab mr note` 或 API 回复讨论）。
- 不同意的：在讨论下说明理由，不改。不要替 reviewer 把讨论标成已解决。
- 只是评价、没有要你做的（比如「已看过，没问题」）：不用回复，不用改。
- reviewer 要求换方案、改动范围明显变大、或者你拿不准该不该改：别自己决定，用 `ask_human` 问我。
- 同一个 MR 改了 3 轮还有新意见：停下来用 `ask_human` 问我还要不要接着改。

## 流水线挂了

- 先看失败的 job 日志：是偶发的（网络、超时、runner 问题）就重跑那个 job（`glab ci retry <job id>`）。
- 是真问题就修，推到同一个分支。

## 有冲突、要变基

- 有冲突：把目标分支合进来或者变基，解决冲突，跑一下相关测试再推。拿不准冲突怎么解就问我。
- 只是落后、没有冲突：先问我要不要变基（`ask_human`）；我说变就变，变基时跑流水线。

## 可以合并了：谁来合

谁来合每个仓库不一样，记在记忆里（派活时给你的「用户的记忆」，`remember` 改）。先看这个仓库的，再看「所有仓库」的；
都没写，就先问我。

- **你直接合**：至少 1 个人批准过，就用 `glab mr merge` 合。合不了（没权限、GitLab 拒绝），就改成去找能合的人。
- **先问我**：用 `ask_human` 问，带上 MR 链接和批准情况，我说合你再合。
  我的回答如果是这个仓库以后都适用的（「这个仓库你直接合就行」「以后找 xx 合」），用 `remember` 记下来，下次就不用再问。
- **要别人合**（记忆里写了是谁）：在 MR 上 @ 他，或者 Slack 私聊他，说清楚可以合了。然后 `wait_for` 盯着 MR，
  `what` 写「等 xx 合 MR !N」；私聊了的话，也盯着那个私信。他合了，你会收到 `mr.merged`。

## 合并之后

- 合并不等于做完。合并之后还有要做的（发布、到线上验证、告诉谁），接着做。怎么发布、发布单找谁批，先看记忆；
  记忆里没有、是问了我或者问了同事才知道的，做完用 `remember` 记下来。
- 都做完了，用 `task_update` 报 `done`；结论要我看的，报 `review`。

## MR 被关了

- 用 `ask_human` 问我：重开、换个方案，还是放弃这个任务。
