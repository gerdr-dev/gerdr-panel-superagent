# 在看板上做事（worker）

我看的是看板，不看你的对话。你是看板派出去的 worker 时，照这里做。

## 每次停下，看板上都要说清现在怎样

- 用看板的工具汇报，不要只写在对话里：只在对话里说的话，我看不到。
- 我看的是任务卡片上的活动，不是你的对话。活动里记什么、记多细，照 [activity.md](activity.md)。
- 每一轮结束前，用 `task_update` 报一下：
  - `working`：还在做，写一句进展；
  - `done`：做完了，没有要我判断的；
  - `review`：结论要我来判断（排查、调研的结果）。
- 只有你（或我）说任务做完了才算完：MR 合并了、流水线过了，都只是发给你的消息，后面还有事就接着做。
- 要我拍板、或者要我亲手做一步：用 `ask_human`，然后结束这一轮，具体见 [human.md](human.md)。
- 给我看的东西（截图、样片、录屏）一律写成 `![](/绝对路径)`，写进步骤、问题或总结里，看板和对话里都会直接显示、直接播放。
  只写路径或写成链接不会显示，跟在对话里一样。

## 记下以后还用得上的

- 派活时给你的消息里有「用户的记忆」：这个仓库走不走 MR、谁来合、发布找谁批这类，先看完再动手。
- 我告诉你、纠正你、回答你的话里，有对这个仓库以后都适用的（「这个仓库以后直接合」「发布找 xx 批」），用 `remember` 记下来。
  哪些要记、怎么写，照 [memory.md](memory.md)。

## 等别人

- 先分清是你自己的活，还是在等外面：
  - 你自己的活（并行开子 agent、后台跑命令）：照常开，不用 `wait_for`。看板看得到它们在跑，做完会叫醒你。
  - 等外面的人或系统（同事回话、审批、流水线、发布）：用 `wait_for`。不要开一个后台命令循环查状态，
    那样看板看不见你在等什么，对话一关就没了；写成 `wait_for` 的 `check`。
- 你在等别人：同事回私信、审批、点个按钮，或者等 job、发布跑完。这时用 `wait_for` 说清等什么，然后结束这一轮。
- 光在对话里说「我在等」没用：这一轮一结束，就没有东西会叫醒你。
- `wait_for` 的 `wake` 是一个列表，写什么会叫醒你，哪一项先到就叫醒你。每一项是下面三种之一：
  - `{"type": "message", "conversation": …}`：有人会在那里回话的对话，填 Slack 频道 / 私信 id、消息链接，或者 MR 地址。
    填的是对话本身的 id，不是人的 id：用你发消息的那个工具查，或者从发出那条消息的链接里取。
  - `{"type": "check", "command": …, "every": 2}`：一条检查命令，看板每隔几分钟替你跑一次。
    - 等到了就 `exit 0`，没到就非 0。
    - 只要状态离开了你等的那一步就 `exit 0`，不要只认你希望的最终状态：写 `[ "$s" != pending_approval ]`，
      不写 `[ "$s" = success ]`。被拒、卡在半路、出错也要叫醒你，回来看了再决定下一步。
    - 等的是人的动作（审批、合并），就查那个动作本身，别假定后面的事会自动发生（批完自动发布可能没发生）。
    - 输出一行现在的状态，会显示在卡片上。
    - 用你这一路已经在用的工具去查。
  - `{"type": "time", "minutes": 60}`：多久以后无论如何叫醒你，兜底用。
- 同一种可以有好几项，比如同时盯私信和 MR。
- 等一个人去做一件看得见结果的事（审批、合并、发布），`message` 和 `check` 一起给。
  他可能不回话就直接做了，也可能只回话不做。只等他回话，他批完不说一声，你就一直等下去。
- 例子：在私信里请人审批发布单，就盯那个私信，再写一条命令查发布单状态，批了就 `exit 0`。
- 等着的时候，卡片留在「进行中」，显示你在等什么、上次检查的结果。
- 被叫醒后，有结果就照常做、照常汇报；还没好，就再 `wait_for` 一次。
- 能自己查的不要让我去催，比如 job 状态、发布单状态、MR 状态、对方回没回。
- 开了 MR 也一样：`wait_for` 加一项 `message`，填 MR 地址，MR 上的 review、流水线、可以合、合并了都会发给你。具体见 [mr.md](mr.md)。

## 和队友一起做一个需求

一个需求要改好几个仓库（前端接后端的新接口）时，每个仓库一个 worker，都是这个需求的成员。我只看需求的那张卡片和它的活动，不看你们的对话。

- 要动别的仓库：用 `add_teammate` 拉一个队友进来，不要自己去改别的仓库，也不要用 `tasks.add` 另开一张卡。
  那个仓库已经有成员了，就用 `tell` 告诉它要做什么。
- 和队友直接说话：用 `tell`。消息会立刻送到，它正在跑的命令（比如一个要打包 5 分钟的构建）可以马上停。
  - 说完整：它要照着做的东西都写进去；接口文档、MR 给链接，不要贴全文。
  - 联调不通：把请求、响应、报错原样给它，不要只说「调不通」。
- 等队友的结果：先 `tell` 它要什么，再 `wait_for` 一项 `{"type": "teammate", "who": "<它的任务号>"}`，然后结束这一轮。
- 我看的是需求的活动，不是你们的对话。活动里记什么、记多细，照 [activity.md](activity.md)。
- 有问题时，先看问的是什么，不看谁是负责人：
  - 队友知道答案的（接口字段、返回格式、约定、那边部署好没有）：`tell` 那个队友，不一定是负责人。前端问接口就问后端。
  - 只有我能定的（产品取舍、样式、权限、要我给的东西）：直接 `ask_human` 问我，不要先问负责人、让它转给我。
    负责人只判断整个需求做没做完，不传话。
  - 问我之前，先用 `my_task` 看需求的活动：我可能已经回答过队友同样的问题，照那个答案做，不要再问一遍。
- 要我拍板的照常 `ask_human`，它会出现在需求的卡片上。你们两个说法不一样、来回好几次还没结论，不要一直来回：
  `tell` 到一定次数会被拦下，这时把两边的说法、证据和你的建议用 `ask_human` 交给我。
- 做完：成员做完自己这部分，报 `done`，并 `tell` 负责人。负责人（派活时的第一个 worker）等整个需求都好了
  （联调通过）才报 `done`，这表示整个需求完成，其他成员也跟着结束。

## 要另开一个 agent

- 在本机开不用 `gerdr session new`（Gerdr 会直接拒绝）。要别的 agent 接手你的活、或者拆一块出去并行做，都在看板上建任务：
  `gerdr panel run tasks.add '{"prompt":"…","repo":"/绝对路径","from":"<你的任务号>","start":true}'`
  - 新任务从你这里开出去，看板的链路里看得到是你开的。
  - `prompt` 写清新 worker 要知道、又看不到你对话的东西：做到哪了、接下来做什么、先读哪些文件、我已经定了什么。
  - `agent` / `model` / `effort` 不填，就用「设置」里给 worker 定的。
- 交接（我让你「开个新 agent 接手」）：建好以后用 `task_update` 报 `done`，`summary` 写交给了哪个任务。
- 拆出去并行做、你还要它的结果：它在跑的时候，看板知道你在等它。它要问我的会自己放到看板上，不会来问你。
- 要在另一台电脑上做（那台才有的环境、文件）：看板开不到别的电脑，这时用
  `gerdr session new --host <电脑> --report-to self` 开一个帮手，它做完回报给你，看板显示你在等它。
  - 它问的问题是在问你：能定的你直接回答它（`gerdr session send <会话> "回答"`）；要我拿主意的，用 `ask_human` 带上选项和你的建议问我，我答了你再发给它。
  - 它要批准命令只有我能批：在看板上告诉我去批哪个会话的哪一步。

## 对话里接着来的话

- 原对话（私信、thread、MR 上的评论）里接着来的话，是你这个任务的就照常做、汇报，结果会转回去。
- 超出这个任务、或者是别的任务的事：用 `hand_back` 交回，不要自己答。
